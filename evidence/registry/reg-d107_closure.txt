REG-D107 closure: sysinfo after lockdown (glibc qsort before 2.37) killed the first shredded commit
==================================================================================================

Found:     2026-10-01, by CI on pull request #226, head 663c0fa: "Test (Python 3.13)" failed
           tests/test_seccomp_runtime_paths.py::test_shredded_commits_need_the_sqlite_syscalls with
           returncode -31 (SIGSYS, the filter's SCMP_ACT_KILL_PROCESS). The same test passed on
           Python 3.11 and 3.12 in the same run, and on this host on every version.
Severity:  P1. The default action is to kill the process, so a gateway that hits it stops serving.
Scope:     Python 3.13 on glibc older than 2.37 (for example Ubuntu 22.04, glibc 2.35), with the
           seccomp filter loaded and a code path that sorts 1 KiB or more after lockdown. The path
           reproduced is cryptographic shredding: the first AES-GCM seal after lockdown.

Root cause (strace -f -k -e trace=sysinfo, CI's own Python 3.13.15 toolcache build, Ubuntu 22.04.5
rootfs, glibc 2.35-0ubuntu3.8, cryptography 50.0.2, no filter fault because sysinfo was allowed):

  sysinfo(...) = 0
   > libc.so.6(sysinfo+0xb)
   > libc.so.6(get_phys_pages+0x25)
   > libc.so.6(qsort_r+0x32a)
   > cryptography/hazmat/bindings/_rust.abi3.so()        (cryptography's bundled OpenSSL)

  Before glibc 2.37, qsort/qsort_r calls __sysconf(_SC_PHYS_PAGES) once per process, on the first
  sort of 1 KiB or more, and caches the answer. __sysconf(_SC_PHYS_PAGES) is get_phys_pages(), which
  is the sysinfo syscall. sysinfo was not in DEFAULT_PROFILE, so the first such sort after lockdown
  was killed. glibc 2.37 and later no longer make this call from qsort; get_phys_pages() itself still
  issues sysinfo on every glibc.

Why Python 3.11 and 3.12 passed (same rootfs, CI's Python 3.12.14 toolcache build):

  On 3.12 the only sysinfo of the process happens during interpreter start-up, before lockdown:

   > libc.so.6(qsort_r+0x32a)
   > libpython3.12.so.1.0(setup_confname_table+0x29)
   > libpython3.12.so.1.0(posixmodule_exec+0x11ae)
   ...
   > libpython3.12.so.1.0(Py_InitializeFromConfig+0x86)

  CPython 3.12's posix module sorts its sysconf name table at import, which caches phys_pages, so
  OpenSSL's later sort makes no syscall. On 3.13 no sysinfo occurs before lockdown; the first one is
  OpenSSL's, after the filter loads (trace line 258, after the seccomp(SECCOMP_SET_MODE_FILTER) at
  line 238). Python 3.11 was not traced; it passed on CI.

Shipped images: deploy/docker/Dockerfile defaults to python:3.12-slim and Dockerfile.airgap uses
python:3.11-slim, so the published images most likely did not hit this. The Dockerfile takes the
base image as a build argument, so a 3.13 build on an older glibc would. Not demonstrated against a
published image. The container-level profile deploy/seccomp/aegis.json already allows sysinfo; only
the gateway's in-process filter lacked it.

Fix:
  aegis/core/seccomp_guard.py   "sysinfo" added to DEFAULT_PROFILE allowed_syscalls, with a comment
                                naming REG-D107. The call is read-only: it returns uptime, load
                                averages and memory totals, which /proc already exposes to the
                                allowed openat. It cannot write, map, execute or create anything.
  tests/test_seccomp_runtime_paths.py
                                test_a_large_qsort_after_lockdown_is_not_killed: under the real
                                default filter, calls get_phys_pages() and a 2 KiB qsort after
                                lockdown. Calling get_phys_pages directly reaches the syscall on any
                                glibc, so the test fails on hosts with glibc 2.37 or later too, where
                                qsort alone would not.

Boundary: one post-lockdown path (shredding) was reproduced and the fix allows the syscall for all
of them. Other code that sorts 1 KiB or more after lockdown (for example a first TLS handshake
through the system OpenSSL) was not enumerated; it is covered by the same allowance, not by a test of
its own. One kernel (6.18.44, x86_64) and two glibc versions (2.35, 2.39) were exercised. No
published image was run with Python 3.13.
