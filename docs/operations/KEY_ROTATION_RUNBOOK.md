# Zero-Downtime Signing-Key Rotation Runbook

This runbook is for security operators and platform engineers rotating HMAC keys without a process restart. It defines the versioned keyring contract, overlap window, rollback and acceptance boundary. The local result does not prove a real secret-manager or orchestrator deployment.

**Last verified:** 2026-08-18 UTC
**Release baseline:** `v3.1.0`
**Scope:** Versioned HMAC keyring for enterprise self-hosted deployments
**Implementation:** `aegis_server.crypto.keyring.RotatingHMACSigner`

## Contract

A keyring contains exactly one `active` key and zero or more `verify` keys. Every signature operation uses the active key and returns a non-secret `key_id` alongside the signature. Verification accepts active and non-expired verify keys during the overlap window. A malformed, weak, unreadable, ambiguous, or unavailable replacement is rejected as a complete snapshot; the last valid snapshot remains active. At process start, no valid snapshot is a hard failure.

The keyring file must be generated by a secret-management process and installed with an atomic rename. It must be owner-readable only. Secret values never appear in logs, metadata, evidence, or release artifacts.

## Rotation sequence

| Step | Operator action | Required observable |
|---|---|---|
| 1 | Generate a new key in the approved secret manager. | Secret-manager audit event; no plaintext in shell history or logs. |
| 2 | Add the new key as `active` and retain the prior key as `verify` with an explicit expiry. | Keyring schema validates; exactly one active key. |
| 3 | Atomically replace the keyring file on each replica or shared control plane. | Each replica logs only the new key ID and activation time. |
| 4 | Send traffic through all three replicas during staggered reload. | No failed durable commits; each record includes the key ID used. |
| 5 | Verify pre-rotation and post-rotation signatures. | Historical records verify with overlap material. |
| 6 | After the overlap window, expire or remove the old key. | Old signatures fail only after the declared expiry; new signatures remain valid. |
| 7 | Preserve the operator event and release the old secret according to the organization’s retention and destruction policy. | No key material appears in the evidence bundle. |

## Keyring schema

```json
{
  "version": 1,
  "active_key_id": "hmac-2026-08",
  "keys": [
    {"key_id": "hmac-2026-07", "secret": "<32+ bytes from secret manager>", "state": "verify", "expires_at": 1796083200},
    {"key_id": "hmac-2026-08", "secret": "<32+ bytes from secret manager>", "state": "active"}
  ]
}
```

The example values are schema placeholders for documentation only. Do not copy them into a deployment.

## Three-replica acceptance test

The current repository contains the signer, deterministic unit contract, and `tools/benchmarks/run_key_rotation.py`. The retained v2 local multi-instance artifact recorded 2,239 signatures across three independent signer instances, observed both key IDs, reported zero failed commits, zero unverifiable records, atomic replacement, and `0o600` keyring permissions. This artifact is retained outside the source tree as `key_rotation_report_v2.json`; it is a local signer exercise, not a Kubernetes, secret-manager, clock-skew, or restart acceptance.

A production three-replica run additionally requires a disposable orchestrated environment with three independent process lifecycles, the actual secret-manager propagation path, independent storage, staggered reload, one delayed replica, restart/replay, and rollback. The acceptance artifact must correlate every committed node with its replica, key ID, timestamp, signature verification result, and request ID.

The gate is **zero failed durable commits during a valid rotation window, zero unverifiable records, zero restart requirement, and correct key IDs before and after rotation**. If the real three-replica environment is unavailable, the result is `UNVERIFIED`, not pass.

## Rollback and kill criteria

Rollback atomically restores the prior valid keyring snapshot while the old key remains within its overlap window. Kill criteria are any unsigned or unverifiable record, key ID not present in the accepted snapshot, a malformed reload that replaces the active snapshot, secret material in logs, failed commit during a declared valid rotation, or a restart required for a key activation that was advertised as zero-downtime.

## Residual risk

The file-backed implementation validates the application state machine. It does not prove secret-manager delivery, filesystem atomicity across a distributed mount, HSM policy, key destruction, replica clock synchronization, or customer-specific recovery behavior. Those properties require deployment evidence and qualified review.
