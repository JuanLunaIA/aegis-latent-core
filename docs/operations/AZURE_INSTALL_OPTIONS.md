# Azure Install Options

**Audience:** anyone choosing how to run the gateway on Azure: founders, platform engineers, SRE, procurement reviewers.
**Scope:** every way this repository supports, or deliberately does not support, running the gateway on Azure, with the advantages, disadvantages and evidence behind each.
**Boundary:** a source-baseline comparison. No option here has target acceptance, and none carries a capacity, availability or cost commitment. Prices are retail list prices fetched on the date stated, not a bill. See [Boundaries](../BOUNDARIES.md).

---

## The constraint that decides everything

The gateway commits each evidence record to its WAL, and synchronizes it, before it returns the response. The WAL takes an exclusive `flock` so that one process writes one chain. That choice makes the **volume type** the deciding factor on Azure:

| Azure storage | Semantics | Fit for the WAL |
| --- | --- | --- |
| Managed Disk (Premium SSD, Standard SSD) | Block device, local POSIX filesystem, one attached VM/pod at a time | **Fits.** `flock` and `fsync` behave as the code assumes. |
| Azure Files (SMB or NFS) | Network filesystem; locks brokered by the server; client caching | **Does not fit.** [Storage Requirements](STORAGE_REQUIREMENTS.md) explains why: locks survive a killed process until the server reclaims them, and `fsync` may be acknowledged before the server commits. |

Every option below either uses a Managed Disk or is marked unsupported because it cannot.

## A. Local evaluation

`deploy/docker` or `pip install`, in `development` enforcement mode. See [Deployment Profiles §1](DEPLOYMENT_PROFILES.md).

| Advantages | Disadvantages |
| --- | --- |
| Free, minutes to start, no Azure account | Authentication and durable evidence are disabled, so records are not evidence |
| Best for reading code and running the tests | Cannot exercise any Azure behavior |

## B. Azure VM kit (recommended starting point)

One Ubuntu 24.04 VM, one Premium SSD data disk holding the WAL, Docker Compose running the gateway, Redis and Caddy (automatic HTTPS on the VM's `cloudapp.azure.com` name). Generated by the [Kit Creator](AZURE_KIT_CREATOR.md); walkthrough in [Azure Quickstart](AZURE_QUICKSTART.md).

| Advantages | Disadvantages |
| --- | --- |
| Smallest bill of any strict option: one VM, one disk, one public IP | **One node.** VM loss, reboot or zone outage means downtime; there is no failover |
| WAL on a Managed Disk with a local ext4 filesystem, so the single-writer lock works as designed | You patch the OS and Docker. Unattended upgrades are the Ubuntu default; reboot policy is yours |
| Strict mode on: Docker's default seccomp and AppArmor profiles satisfy the startup checks | Secrets are generated on the VM and stored in a root-only file, not in Key Vault. Anyone with root on the VM holds the signing key |
| One command, no Kubernetes knowledge, no pre-existing Azure resources | Redis is one container on an internal-only network, password-protected, without TLS; rate-limit state is lost on restart |
| Budget alert created with the kit | Premium SSD is not documented here as power-loss-protected; [Storage Requirements](STORAGE_REQUIREMENTS.md) applies in full |
| Disk is detached, not deleted, when the VM is replaced (`deleteOption: Detach`) | Public IP is exposed; only ports 80 and 443 (and SSH from one CIDR, if you allow it) are open |
| Reproducible: Bicep + a checksum file, no secrets in the kit | Backups are yours: nothing in the kit snapshots the WAL disk (see [Backup and Restore](BACKUP_RESTORE.md)) |

Use it for pilots, single-tenant deployments and evaluation on real infrastructure.

## C. AKS

`deploy/azure/aks/`: AKS with Cilium, workload identity, Secrets Store CSI driver reading Key Vault, Envoy Gateway and cert-manager for TLS, Helm chart in strict mode, one WAL volume per replica (StatefulSet).

| Advantages | Disadvantages |
| --- | --- |
| Two replicas spread across zones and hosts | **Each replica keeps its own chain.** There is no global ordering ([Deployment Profiles §3](DEPLOYMENT_PROFILES.md)) |
| Secrets in Key Vault, pulled by workload identity; no key on a node | `bootstrap.sh` assumes an ACR, a Key Vault, a managed identity and an existing principal mapping already exist; the repository does not create them |
| Managed control plane, rolling upgrades, network policy | The script's own cost note puts two `Standard_B2als_v2` nodes with OS disks near 3.1 USD/day at retail in `chilecentral` on 2026-09-16, before load balancer, ACR and Key Vault; that figure is the operator's annotation and was not re-measured here |
| Path to more replicas and autoscaling | Kubernetes skills required; a failed Helm upgrade can lock the release (the script contains recovery logic for that) |
| Zone-redundant placement of pods | The operator authored it against one subscription and region; treat other targets as untested |

Use it when you need more than one replica and can accept one chain per replica.

## D. Azure Container Apps

**Not supported.** Recorded so nobody re-derives the dead end.

| Reason | Detail |
| --- | --- |
| Persistent storage | Container Apps persistent volumes are Azure Files. Azure Files fails the WAL constraint above |
| Kernel controls | Strict startup requires seccomp and an LSM label on the process. A managed container platform does not let you select those profiles |
| Evidence | Without a local disk, the commit-before-response guarantee has nothing to stand on |

This reasoning rests on the documented behavior of the platform and this repository's storage analysis; it was **not** tested against a live Container Apps environment.

## E. Helm on any Kubernetes on Azure

`deploy/helm` on a cluster you already run (AKS, or another distribution on Azure VMs).

| Advantages | Disadvantages |
| --- | --- |
| Reuses your cluster, ingress, identity and secret manager | You supply Redis, the secret, the StorageClass and network policy; the chart installs none of them |
| Chart is linted and rendered in CI | CI does not deploy to Azure ([Platform Compatibility](../PLATFORM_COMPATIBILITY.md)) |
| Same per-replica WAL model as option C | Choose a Disk-backed StorageClass, never an Azure Files one |

## Decision guide

| You need | Choose |
| --- | --- |
| To look at the code | A |
| A strict pilot running on Azure this week, lowest cost | B |
| Several replicas, zone spread, Key Vault-held secrets | C or E |
| Managed serverless containers | None; D is unsupported |
| Non-repudiation (attributing records to a party) | Any option plus an asymmetric signing key in an HSM-backed store; see `REG-H08` and [Registry Human Pack](../REGISTRY_HUMAN_PACK.md) |

## Cost method

`python deploy/azure/kit-creator/aegis_azure_kit.py estimate --region <r> --vm-size <s>` fetches the retail price from `prices.azure.com` at run time. Results on 2026-09-26 UTC for `Standard_B2als_v2`: `eastus` 0.0376 USD/hour (about 27.45 USD per 730-hour month), `chilecentral` 0.0526 USD/hour (about 38.40), both excluding disks, IP, bandwidth and any credit. Two of those VMs for 24 hours are about 2.52 USD at the `chilecentral` price before disks, which is consistent with the AKS script's own 3.1 USD/day note. Availability differs by subscription: on the subscription used for the [Azure Benchmarks](../benchmarks/AZURE_BENCHMARKS.md), `Standard_B2als_v2` was creatable in `chilecentral` and not offered in `eastus`, so run `doctor` for your subscription and region.
