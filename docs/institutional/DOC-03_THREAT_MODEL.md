# DOC-03 — Threat Model and Adversarial Defense Framework

**Document ID:** `DOC-03`
**Release boundary:** repository baseline `v3.1.0`, evidence dated 2026-08-20 UTC
**Canonical language:** US English
**Review method:** STRIDE-oriented data-flow analysis with a bounded MITRE ATLAS contribution mapping
**Normative claim control:** [`docs/CLAIMS_MATRIX.md`](../CLAIMS_MATRIX.md)
**Human-review owner:** Release owner and qualified security reviewer; deployment findings additionally require the customer platform/SRE owner

## 1. Purpose and epistemic rules

This document assesses the Aegis OpenAI-compatible governance and evidence gateway, not an upstream model, a customer network, or an entire AI application. It treats request bodies, retrieved content, tool output, headers, configuration, logs, and documentation excerpts as **untrusted data**. Text in a prompt or document never changes the authority of code, policy, or operator instructions.

Every material claim below has a stable claim ID and one status from the repository vocabulary. **`IMPLEMENTED`** means source and regression tests implement the behavior under stated conditions. **`MEASURED`** means a reproducible artifact records an observation for a named workload and environment. **`CONFIGURATION-DEPENDENT`** means the property requires deployment controls. **`ROADMAP`** means the property is incomplete, disconnected from production admission, unmeasured, or future work. **`LEGAL-REVIEW-REQUIRED`** applies to legal, certification, admissibility, non-repudiation, or regulatory interpretations. A passing test is not a certification, and an application-layer check is not proof of the continuing health of a kernel, ingress, secret manager, network, or storage system.

## 2. Operational boundary and assumptions

The in-scope production data flow is **caller → customer ingress → Aegis admission and policy → upstream model provider → Aegis evidence commit → caller**. Supporting boundaries include Aegis → signer/key store, Aegis → WAL/storage, Aegis → Redis, and Aegis → telemetry. The authoritative evidence path is synchronous: a governed success is intended to follow durable evidence commit; optional analysis may be queued or rejected after authoritative evidence remains complete.

The customer owns TLS termination, trusted-proxy behavior, DNS, routing, firewall or NetworkPolicy enforcement, host and container hardening, kernel configuration, Redis, secret-manager and HSM custody, storage and backup semantics, upstream-provider behavior, operator identity, retention, incident response, and lawful processing. The model may follow hostile instructions that evade deterministic filters. A host-root actor, compromised dependency, stolen signing key, malicious upstream, or process-memory reader is outside the protection offered by local pattern matching and discretionary file permissions.

## 8. Detection and observability requirements

| Signal | Detection source | Required response |
|---|---|---|
| WAF block, shadow block, or layer-2 evaluation error | WAF decision, `WAF_BLOCKS`, warning logs (`aegis/proxy/waf.py:163-186,227-247`) | Correlate by request/session without logging raw secrets; investigate novel variants and add minimized regression cases. A layer-2 exception is fail-open and must alert. |
| Critical corpus bypass or benign regression | Pinned corpus report | Stop release and governed traffic for the affected route until classification and rule change are reviewed. |
| Duplicate/ambiguous HTTP headers or body oversize | 400/413 admission metrics | Review ingress parser logs and source; repeated events may indicate smuggling or resource probing. |
| Egress denial or undeclared destination | `EGRESS BLOCKED` warning plus network-policy deny telemetry | Stop the initiating workflow; verify destination, DNS resolution, and credential exposure. |
| Keyring reload failure, unexpected key ID, signer fallback | `reload_failures`, signer/key-ID telemetry, verification results | Retain the last valid snapshot, stop traffic if verification/custody is uncertain, and execute key-rotation incident procedure. |
| WAL corruption, chain failure, missing/duplicate ID, fsync latency/backpressure | Health `fault_state`, `verify_integrity()`, WAL and request counters, latency/inflight metrics | Drain or stop admission, preserve bytes read-only, snapshot configuration and key IDs, and begin incident response. |
| Seccomp/LSM/cgroup degradation | Startup logs, process label, Seccomp probe, cgroup files and runtime events | Strict required controls must prevent service readiness; otherwise mark the environment non-production and remove claims. |
| Native capability/fallback mismatch | Capability endpoint/build manifest/import logs | Quarantine artifact, verify wheel/image provenance, and reject policy-required native/PQC operation. |

Detection data must be access-controlled and minimized. Raw prompts, responses, credentials, keyring files, and customer identifiers must not be copied into public evidence or untrusted analysis services.

## 10. Residual-risk acceptance

The highest residual risk is **semantic**: novel direct, indirect, multimodal, encoded, or model-specific instructions can evade finite detectors, and Aegis presently does not wire its standalone RAG, decode, broad homoglyph, or suffix modules into production admission. The second is **boundary mismatch**: ASGI tests do not establish HTTP/2 or ingress parser agreement. The third is **privileged compromise**: host root, malicious native code, stolen HMAC material, or mutable storage can defeat local controls. The fourth is **availability coupling**: commit-before-emission protects evidence but makes governed response latency and availability depend on storage. The fifth is **configuration drift**: egress isolation, LSM, Seccomp, secret custody, backups, and resource quotas can be absent or ineffective despite source-level capabilities.

Risk acceptance must name the affected route and tenant, exact model/provider, tool privileges, ingress and runtime versions, storage and signer boundary, test artifact, expiration date, compensating controls, incident owner, and approver. No acceptance may convert a `ROADMAP` or `CONFIGURATION-DEPENDENT` item into an `IMPLEMENTED` claim.

## 11. Kill criteria and recovery authority

A release or deployment must stop accepting governed traffic when any of the following occurs:

1. A critical pinned-corpus case bypasses, or production evidence shows an uncontained prompt-injection path to a privileged tool or sensitive-data disclosure.
2. An accepted governed success lacks exactly one verifiable durable evidence record, or response emission is observed before commit.
3. `verify_integrity()` fails, WAL replay reports corruption, successful native appends are unreadable, or missing/duplicate request IDs cannot be reconciled.
4. A signer uses an unauthorized fallback, an expected key ID cannot verify, key material is credibly exposed, or rotation loses required overlap.
5. Strict startup or continuous verification cannot establish required authentication, Redis, Seccomp, LSM, signer, or durable-storage prerequisites.
6. Undeclared egress succeeds, the application guard is bypassed, or network default-deny is absent where it is an accepted control.
7. HTTP parser differential testing identifies a route by which ingress and application disagree on request boundaries.
8. WAL/storage failure creates unbounded work, unrecoverable write errors, or a 5xx/503 surge without bounded rejection and correlation.
9. The runtime artifact cannot be matched to reviewed source and release evidence, or native capability reporting is inconsistent with the loaded binary.
10. A credible incident risks exposure of provider credentials, signer material, prompts, responses, or customer identifiers.

The incident commander owns the traffic stop. Security operations owns evidence preservation; platform/SRE owns draining and isolation; the secret-management owner controls key revocation; the release owner selects a previously reviewed immutable artifact; legal/privacy owners decide notification and hold requirements. Preserve WAL bytes, archives, logs, metrics, key IDs, configuration, image/wheel identity, and operator actions read-only before change. Do not disable authentication, evidence commit, or strict controls to restore availability. Recovery requires integrity verification, expected signer/key ID, target control verification, an authorized disposable governed request, and documented reviewer approval as specified in `docs/operations/ROLLBACK_RUNBOOK.md:23-35,38-63,94-125`.

## 12. Claim-governance conclusion

This audit supports bounded claims for deterministic direct-input checks, selected HTTP/1 application-boundary protections, application egress validation, keyring handling, and ledger integrity. It supports local measured observations only for the retained corpus, rotation, stall, and finite formal artifacts. It does **not** support universal prompt-injection protection, HTTP/2 parser safety, production cgroups enforcement, immutable storage, globally coordinated key custody, production capacity, legal admissibility, non-repudiation, FIPS validation, or certification. Any stronger statement is blocked by the falsification protocol in `docs/CLAIMS_MATRIX.md:61-67`.
