# Dependency risk register

Per-dependency disposition for components carrying deserialization, evaluation,
execution or remote-fetch primitives, and for components whose maintenance
state is itself the risk.

This register records decisions and the evidence behind them. The machine-
checked inventory lives in `docs/security/DEPENDENCY_TRIAGE.md`, regenerated by
`scripts/triage/dependency_triage.py`; the two are meant to be read together.

## Scope of the input evidence

This review was commissioned against two exports, `dependency-alerts-report.pdf`
and `alerts.pdf`. One arrived; the other did not, and what arrived in its place
is a different kind of document.

**Received and fully ingested.** The dependency alerts report (Socket.dev,
generated 2026-09-09 16:06 UTC, filters `action: error, monitor, warn`) carries
**100 alert rows** against this repository's dependency graph. Every row is
parsed by `scripts/triage/parse_socket_report.py` into
`evidence/dependency-scan/2026-09-09/socket-dependency-alerts.json` and merged
through `dependency_triage.py --scan-export`. All 100 appear exactly once in
the row ledger of `docs/security/DEPENDENCY_TRIAGE.md`: 86 matched a locked
component and carry its bucket; 14 name development tooling or optional extras
the scanner reaches through `pyproject.toml`, or a dependency removed since the
scan — `generic-array 0.14.7` is in that last group, dropped from `Cargo.lock`
by the digest-stack migration recorded below. The parser exits non-zero on any
row it cannot parse, because a silent drop would break the guarantee this
paragraph makes.

**`[BLOCKED: `alerts.pdf` was not supplied.]`** A Socket **Threat Feed sample**
was supplied instead. That is an ecosystem-wide sample of packages the scanner
flagged across npm and PyPI generally — not an alert set against this
repository. Its 30 rows are ingested and listed in the same ledger for
completeness, and **none of the four packages it names
(`@whalent/agent`, `@whalent/agent-core`, `triviumdb`,
`@hypelens/polymarket-place`) appears in any Aegis lock file**, so none is
actionable here. If `alerts.pdf` exists and differs from the dependency alerts
report, its rows are still absent from this review.

Independently of both exports, every dependency the repository *locks* was
enumerated from `requirements.lock`, both `Cargo.lock` files and both
`package-lock.json` files, queried against OSV, and classified — 557
components. The two methods disagree in useful ways, and the ledger records
both rather than reconciling them away.

Findings below rest on one of three evidence classes, marked per row:

- **[OBSERVED]** — read directly from a lock file, a package manifest, installed
  metadata, or dependency source in this tree.
- **[MEASURED]** — produced by running a tool and reading its output.
- **[UNREPRODUCED_EXTERNAL_CLAIM]** — asserted by the commissioning brief or a
  third-party scanner and not independently confirmed here. These are recorded
  because they may well be true; they are marked because nothing in this
  repository establishes that they are.

## Dispositions

### Machine-learning stacks — EXCLUDE-FROM-CORE (already satisfied)

The brief describes `torch 2.14.0` and `transformers 5.16.1` as **direct**
dependencies requiring relocation to an optional extra.

**[OBSERVED]** They are not direct dependencies, and the relocation the brief
asks for is already the state of the tree:

| package | brief's claim | observed |
| --- | --- | --- |
| `torch` | direct, 2.14.0 | declared only under the `gpu`, `vllm` and `hf` extras at `>=2.0.0`; absent from `requirements.lock` |
| `transformers` | direct, 5.16.1 | declared only under the `hf` extra at `>=4.40.0`; absent from `requirements.lock` |
| `vllm` | present | declared only under the `vllm` extra at `>=0.4.0`; absent from `requirements.lock` |
| `sentencepiece` | transitive, native, 0.2.2 | absent from `requirements.lock` entirely |

`requirements.lock` is the hash-pinned set installed into a released image, so
absence from it means the primitives in question — `torch`'s `pickle.loads` and
`exec` paths, `transformers`' `trust_remote_code`, `vllm`'s multiprocess RPC —
are not reachable from a default gateway install at all.

**Disposition: EXCLUDE-FROM-CORE, enforced.**
`tests/security/test_dependency_containment.py` fails the build if any of these
becomes a core runtime dependency or appears in the runtime lock, and separately
asserts the extras still exist, so containment cannot be confused with removal.

The hardening the brief specifies for a deployment that *does* enable an ML
extra — `TORCH_FORCE_WEIGHTS_ONLY_LOAD=1`, never calling `torch.load` on
untrusted input, never enabling `--trust-remote-code` — remains correct advice
for that deployment and is **not** enforced by this repository, because the
repository does not construct those processes. Stating otherwise would claim
control Aegis does not have.

### `pyyaml` — ISOLATE (enforced by test)

**[OBSERVED]** PyYAML is a transitive dependency at 6.0.3. Its
`FullConstructor` and `UnsafeConstructor` instantiate arbitrary Python objects
from a document, and `yaml.load` selects `FullLoader` by default.

**[OBSERVED]** Every YAML parse site in the first-party tree already uses
`yaml.safe_load` or `yaml.safe_load_all`. There were no unsafe sites to
remediate. The brief's proposed `aegis/security/yaml_safe.py` wrapper was
therefore **not** created: a wrapper module that every call site must remember
to import is a weaker guarantee than a test that fails when any call site stops
being safe, and it would add an indirection with nothing behind it.

**Disposition: ISOLATE.** `tests/security/test_yaml_safe_loading.py` scans the
first-party Python tree and fails on `yaml.load(` without an explicit safe
loader, and on `yaml.unsafe_load` / `yaml.full_load` anywhere. It also asserts
its own detector fires on known-bad snippets, and that PyYAML's
`SafeConstructor` still refuses a `!!python/object/apply` tag — so the gate
fails if the property is lost either in this repository or upstream.

### `cryptography` — ISOLATE (verified, no shell path)

The brief flags `cryptography 50.0.1` for "shell access" and asks that the
wheel's provenance be confirmed and any shell-out refactored.

**[OBSERVED]** The installed distribution's metadata names
`The Python Cryptographic Authority and individual contributors
<cryptography-dev@python.org>` as author and `https://github.com/pyca/cryptography`
as source: it is the genuine PyCA package, not a typosquat. It is pinned in
`requirements.lock` at an exact version with a full set of `--hash=sha256:`
digests, so `pip install --require-hashes` rejects any substituted artifact.

**[OBSERVED]** No Aegis code invokes a shell through it. The flag most plausibly
reflects OpenSSL build tooling in the source distribution, which is not present
in the wheels this project installs.

**Disposition: ISOLATE.** No change required. The pin and the hash set are the
control.

### `cffi` — ISOLATE

**[OBSERVED]** Transitive under `cryptography`, at 2.1.1. Its bindings resolve
to the OpenSSL bundled in the `cryptography` wheel. No Aegis code calls
`cffi.dlopen` with a runtime-supplied path, so there is no attacker-controllable
library-loading path through it.

**Disposition: ISOLATE.** The wheel pin and hash set are the control.

### `numpy`, `rich`, `mypy`, `msgspec`, `pillow` — ISOLATE

**[OBSERVED]** `numpy` is a core runtime dependency; the others are development
or build tooling and are absent from `requirements.lock`. `pillow` and
`msgspec` are not installed at all.

The primitives the brief lists for these — `numpy`'s regeneration-checker
pickle, `rich`'s `Style.meta` pickle and OSC8 sequences, `dmypy`'s
`--options-data` pickle, `msgspec`'s test-suite `exec`, `pillow`'s vendored
download script — are **[UNREPRODUCED_EXTERNAL_CLAIM]**. They were not
confirmed against upstream source here. They are recorded because the
disposition does not depend on whether they are true: none of these components
is fed attacker-controlled input by anything in this repository, and CI runs
them only over repository-controlled files.

**Disposition: ISOLATE.** No code change. The control is that the sinks are not
reachable from request data.

## Remediated: `block-buffer` panic corruption in the digest hot path

**[OBSERVED]** Row `0.31` of the scanner report carries a `Medium CVE` alert
against `block-buffer 0.10.4`, CVSS 6.3, with an **empty CVE ID field**. That
empty field is the whole reason this was nearly missed: an OSV query for
`block-buffer` returns no advisory at any version, so a review that consulted
only OSV — as an earlier revision of this document did — concluded no primary
source existed. It did; it simply had no CVE identifier to look up.

The advisory reports that a caught panic can leave the cursor of `EagerBuffer`
or `ReadBuffer` violating that type's invariant, after which `get_pos()`
reaches an `unreachable_unchecked` — undefined behaviour. `block-buffer 0.10.4`
was pinned transitively through `digest 0.10`, which put it under **every
SHA-256 and HMAC call on the evidence path**.

**Disposition: REMEDIATED.** The digest stack moved to `sha2` 0.11 / `hmac`
0.13, which resolves `block-buffer 0.12.1`. Upstream fixed it by wrapping both
windows in a `ResetGuard` whose `Drop` restores the invariant during unwind.

**[MEASURED]** `aegis_rust_v2/tests/block_buffer_panic_safety.rs` ports both
published proofs — a panic inside `compress`, and a panic inside `gen_block` —
plus a third for a panic inside `read_fn` that neither proof covers. All three
pass under `cargo +nightly miri test`, so the remediation is demonstrated on
the version this crate links rather than inferred from a version number.

Hash output is unchanged: FIPS 180-4 and RFC 4231 vector tests in
`aegis_rust_v2/src/ledger.rs` compare full digests against published external
vectors, and the Python↔Rust MMR parity suite passes with the extension
required.

**Boundary.** Three panic shapes on one version pass Miri under Stacked
Borrows. That is not a proof that the crate is free of unsoundness, and Miri
covers only the paths a test actually executes.

## Maintenance risk: the post-quantum signing stack

This is the most significant finding of the review, and it was not in the
brief.

**[MEASURED]** Querying OSV for all 557 locked components returned four
advisories, all of them RUSTSEC notices with no fixed version:

| advisory | crate | version | scope |
| --- | --- | --- | --- |
| `RUSTSEC-2026-0166` | `pqcrypto-mldsa` | 0.1.2 | **direct dependency** of `aegis_rust` |
| `RUSTSEC-2026-0162` | `pqcrypto-traits` | 0.3.5 | **direct dependency** of `aegis_rust` |
| `RUSTSEC-2026-0163` | `pqcrypto-internals` | 0.2.11 | transitive under `pqcrypto-mldsa` |
| `RUSTSEC-2024-0436` | `paste` | 1.0.15 | transitive under `pqcrypto-mldsa` |

All four share one root cause: the PQClean project, whose C implementations the
`pqcrypto-*` crates wrap, is being archived in or after July 2026. After that
no upstream security patch will be applied.

**What this is not.** None of these is an exploitable defect. They are
unmaintained-status notices, and there is no fixed version to upgrade to.
Filing them as CVEs would produce a release gate nobody can satisfy, which is
why `dependency_triage.py` separates "an advisory with a fixed version" from
"an advisory with none" and routes these to `BUCKET-5`.

**Why it still matters here.** `pqcrypto-mldsa` provides ML-DSA-65 (FIPS 204),
the post-quantum signing path — a component whose entire value proposition is
long-horizon durability. A signing implementation that will stop receiving
security fixes is a materially different proposition from one that will not,
and a buyer evaluating the post-quantum claim is entitled to know that.

**Disposition: TRACK A MIGRATION.** The upstream advisory names the `ml-dsa`
crate, a pure-Rust FIPS 204 implementation, as the successor. Migrating is out
of scope for this change: it replaces a cryptographic implementation, which
requires its own vector-level verification against FIPS 204 and its own
assessment of the constant-time properties `SECURITY.md` already declines to
claim for the current backend. Doing it inside a supply-chain remediation would
bury a crypto change in a dependency sweep.

Residual risk while this stands: **accepted and recorded**. The advisory does
not report a defect in the current implementation; it reports that a future one
would not be fixed upstream.

## Rejected remediations

Recorded so a later reviewer does not re-propose them without the reason.

**A `yaml_safe.py` wrapper module.** Rejected in favour of the test gate, for
the reason given above.

**Removing `uvloop` from the core.** The brief classifies `uvloop 0.22.1` as a
direct GPL-2.0/3.0 dependency and a release blocker requiring relocation to an
optional extra. **[OBSERVED]** Both halves are wrong. Its installed
distribution declares `MIT License` with trove classifiers for both the MIT and
Apache-2.0 licences, and ships `LICENSE-MIT` and `LICENSE-APACHE` in its
`dist-info`; there is no GPL grant. It is also not a direct dependency — it
arrives transitively through `uvicorn[standard]`. There is no licence defect to
remediate, and relocating it would degrade the event loop for no benefit.

**Patching Next.js `mkcert.js`.** **[OBSERVED]** The file exists in the
installed `next@16.3.4` at `dist/lib/mkcert.js`, and the brief's description of
it is accurate: it fetches a release binary over plain `fetch` with no signature
or digest verification, and passes the requested hosts into
`execSync` interpolated into the command string without shell escaping.

It is nonetheless not remediated here, because it is upstream code on a path
this repository never takes: it runs only under `next dev --experimental-https`,
and the dashboard's `dev` script is plain `next dev`. Vendoring a patch into
`node_modules` would not survive an install, and forking Next.js over a
dev-server convenience is disproportionate.

**Control instead of a patch:** `tests/security/test_dependency_containment.py`
asserts that no script in either JavaScript project enables
`--experimental-https` and that `next.config.ts` does not set
`experimentalHttps`. The unsafe path stays unreachable, and the test fails if
somebody adds the flag.

## Boundary

This register records engineering dispositions and the evidence for them. It is
not an assurance that the dependency set is free of vulnerabilities, not an
external audit, and not a certification of any kind. Advisory coverage is
bounded by what OSV held on the date recorded in
`docs/security/advisory_snapshot.json`; a component with no advisory is a
component with no *known* advisory. The scanner exports this review was
commissioned against were unavailable, so any finding visible only to those
scanners is absent from this document.
